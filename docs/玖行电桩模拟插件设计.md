## 1. 插件定位与目标

“玖行电桩模拟”插件用于模拟电桩与远端平台之间的 TCP 协议通信过程，核心能力包括：

- 通过 TCP Client 主动连接远端 TCP Server。
- 基于十六进制字节命令执行指定业务交互流程。
- 以可视化协议-桩-枪-车网络拓扑方式展示设备结构与连接关系。
- 通过流程配置实现“流程组合式”模拟，不把流程逻辑硬编码在 UI 中。
- 支持玖行设备协议的导入/导出，并按协议能力动态判定流程是否可用。
- 支持协议与设备持久化存储，且支持后续修改编辑。

## 2. 技术栈与核心依赖

## 2.1 通讯与协议层

- 通讯协议：TCP（Client -> Remote Server）。
- 报文格式：16 进制字节命令（可映射到命令字、长度、载荷、校验等字段）。
- 核心模块建议：
  - `TcpSessionManager`：连接/断连/重连/心跳维护。
  - `HexCodec`：Hex 字符串与字节数组互转、校验。
  - `ProtocolExecutor`：按流程步骤执行收发与状态推进。
  - `FlowRegistry`：加载流程配置、流程组合与版本管理。

## 2.2 可视化层

- 网络拓扑图：AntV G6（动态生成、增删节点、自动布局/分层）。
- 节点类型：
  - 协议节点（根节点）
  - 电桩节点
  - 充电枪节点
  - 车辆节点
- 边类型：
  - 协议 -> 桩
  - 桩 -> 枪
  - 枪 -> 车辆

## 2.3 语义模型与线格式映射（多协议版本）

**目标**：用一套**业务语义**（kWh、元、秒、物理电压电流等）驱动模拟；不同 `protocolId` 仅影响「如何写成 Hex 载荷」，避免在 `ProtocolExecutor` 内散落魔法数。

**约定**

1. **标尺常量**（与平台 Java `CovertConst` 对齐，**唯一定义**在 `jx-wire-scale.ts` 的 `WIRE_SCALE`；`jx-wire-025` 等模块 re-export 以便就近引用）：  
   - `ONE_POINT`：`0.1`（电压 V、电流 A）  
   - `TWO_POINT`：`0.01`（元）  
   - `FOUR_POINT`：`0.0001`（kWh；段电价/段服务费单价为 **元/kWh**）
2. **`0x25`**：`build025PayloadWire` → `encodeCm25Data222Layout`（`jx-wire-025.ts`），布局与 `CM25Data222` 一致；`WorkInfoHandler224` 对**时长**在平台侧按 **`÷60`** 为分钟，模拟器线格式仍写**秒**。注册扩展：`register025WireEncoder` / `resolve025WireAdapter`。
3. **`0x30`**：`build030PayloadWire`（`jx-wire-030.ts`），默认 `encodeCm30DefaultLayout`；`register030WireEncoder` / `resolve030WireAdapter` 供版本分叉。
4. **`0x21`**：`make21Payload`（`jx-wire-021.ts`），默认 `encodeCm21DefaultLayout`；`register021WireEncoder` / `resolve021WireAdapter` 供版本分叉。`ProtocolExecutor` 对 tests 仍 `export { make21Payload }` 保持原入口。
5. **`0x20`**：`buildCm20PayloadFrom1f`（`protocol-executor.ts`）按 **`CM20Data218`** 由下行 **`0x1F` 数据域去掉账户余额 4 字节**，必要时保留「计费模型选择=2」后的费率扩展尾，再追加执行结果/失败原因；**不与 `0x1F` 全长简单拼接**。
6. **`0x23` / `0x33`**：已具备 `order23WireProfileFromProtocolId` 与 `encodeOrder23Or33Payload`（`jx-order23-wire-map.ts`），与上表同一思路，新协议在 profile 中增分支即可。
7. **推广原则**：其它上行命令新增或改版时，优先「语义层 + 按 `protocolId` 选编码器」；Executor 只做调度与状态，**不写散落缩放公式**。

## 3. 业务流程模型（可配置编排）

## 3.1 首批内置流程

当前支持以下流程模板：

1. 链接认证登录流程  
2. 远端控制启动流程  
3. 本地 VIN 启动流程  
4. 远端控制启动 VIN 鉴权流程

## 3.2 流程配置设计

每个流程由一组步骤组成，步骤类型建议：

- `send`：发送 Hex 命令
- `expect`：等待指定响应（可带超时）
- `branch`：按响应码分支
- `retry`：失败重试
- `delay`：步骤间等待
- `emitState`：更新设备状态（桩/枪/车）

示意结构：

```json
{
  "flowId": "remote-start-vin-auth",
  "name": "远端控制启动VIN鉴权流程",
  "version": "1.0.0",
  "steps": [
    { "type": "send", "cmd": "AA5501..." },
    { "type": "expect", "match": "AA5502", "timeoutMs": 3000 },
    { "type": "branch", "by": "resp.code", "cases": { "00": "ok", "01": "fail_auth" } }
  ]
}
```

## 3.3 流程组合能力

- 支持将多个流程模板串联为“场景流程”：
  - 例如 `登录流程 -> VIN鉴权 -> 远端启动`。
- 场景定义由配置驱动，后续新增流程不需要改动主界面结构。

## 3.4 协议导入/导出与能力校验

- 支持导入“协议定义包”（JSON）与导出当前协议定义。
- 协议定义包含：
  - 协议标识与版本（`protocolId` / `version`）
  - 命令字典（命令编码、参数定义、响应映射）
  - 流程模板（步骤与所需命令/参数）
- 导入后系统执行能力校验，逐条标记流程：
  - `supported`：命令与参数完整，流程可执行
  - `partial`：部分命令/参数缺失，流程受限（可展示缺失清单）
  - `unsupported`：关键命令缺失，流程不可执行
- 典型场景：导入另一版本协议后，部分旧流程因缺少命令或参数而自动不可用。

## 3.5 协议导入 JSON 格式与要求（落地规范）

本节定义插件可导入的协议 JSON 结构。导入实现必须按本规范做严格校验，确保可回滚、可诊断、可兼容判定。

### 3.5.1 顶层结构

```json
{
  "schemaVersion": "1.0.0",
  "protocolId": "jx-v2.25-core",
  "protocolName": "玖行协议V2.25",
  "version": "2.25.0",
  "vendor": "jiuxing",
  "source": "imported",
  "description": "基于玖行桩协议2.25整理",
  "commandCatalog": {},
  "flowTemplates": [],
  "meta": {
    "author": "team-a",
    "createdAt": "2026-04-22T09:30:00Z",
    "updatedAt": "2026-04-22T09:30:00Z"
  }
}
```

字段要求：

- `schemaVersion`：必填，当前仅接受 `1.x`。
- `protocolId`：必填，`^[a-z0-9][a-z0-9-_]{2,63}$`，全局唯一（系统内唯一键）。
- `protocolName`：必填，`2~64` 字符，用于拓扑根节点展示。
- `version`：必填，建议语义化版本（如 `2.25.0`）。
- `vendor`：可选，默认 `jiuxing`。
- `source`：必填，`builtin | imported`。
- `commandCatalog`：必填，至少包含 1 条命令定义。
- `flowTemplates`：必填，至少包含 1 个流程模板。
- `meta`：可选，记录导入来源与审计信息。

### 3.5.2 `commandCatalog` 结构

键名必须是命令码小写形式（如 `0x1f`）。值结构如下：

```json
{
  "0x1f": {
    "cmd": "0x1f",
    "name": "平台下发充电命令",
    "direction": "down",
    "requiredParams": ["timeTag", "gunNo", "orderNo", "userId", "controlMode", "controlParam"],
    "optionalParams": ["userType", "orgCode", "chargeMode", "startMode", "scheduleStartTime", "opCode", "priceModelSelect"],
    "resultFields": ["executeResult", "failReason"],
    "links": {
      "requestOf": null,
      "responseOf": null,
      "nextCmds": ["0x20", "0x21", "0x22"]
    }
  }
}
```

字段要求：

- `cmd`：必填，必须与对象 key 一致。
- `name`：必填，`1~80` 字符。
- `direction`：必填，`up | down`。
- `requiredParams`：必填数组，不可为空字符串项，不可重复。
- `optionalParams`：可选数组，不可与 `requiredParams` 重复。
- `resultFields`：可选数组，用于 `branch` 步骤结果判定。
- `links`：可选，用于流程自动编排提示，不参与硬校验。

参数命名约束：

- 使用 `camelCase`（如 `orderNo`、`allowChargeFlag`）。
- 同义参数名统一（例如只允许 `orderNo`，禁止同时出现 `order_id`）。
- 建议参数枚举与 `玖行桩协议2.25.md` 第 8 章保持一致。

### 3.5.3 `flowTemplates` 结构

```json
[
  {
    "flowId": "remote-start",
    "name": "远端启动",
    "version": "1.0.0",
    "scene": "remote-control",
    "requiresCommands": ["0x1f", "0x20", "0x21", "0x22"],
    "requiresParams": ["gunNo", "orderNo", "controlMode", "controlParam"],
    "steps": [
      { "id": "s1", "type": "send", "cmd": "0x1f" },
      { "id": "s2", "type": "expect", "cmd": "0x20", "timeoutMs": 3000 },
      { "id": "s3", "type": "expect", "cmd": "0x21", "timeoutMs": 5000 },
      {
        "id": "s4",
        "type": "branch",
        "by": "executeResult",
        "cases": { "1": "success", "2": "fail" }
      }
    ]
  }
]
```

字段要求：

- `flowId`：必填，当前协议内唯一，`^[a-z0-9][a-z0-9-_]{2,63}$`。
- `requiresCommands`：必填，至少 1 个命令。
- `requiresParams`：可选，声明流程级参数依赖。
- `steps`：必填，至少 1 步，且 `id` 在流程内唯一。
- `type`：只允许 `send | expect | branch | retry | delay | emitState`。

步骤约束：

- `send` 必须有 `cmd`。
- `expect` 必须有 `cmd` 与 `timeoutMs`（`100~120000`）。
- `branch` 必须有 `by` 与 `cases`，且 `cases` 至少 1 个分支。
- `retry` 必须有 `maxRetries`（`0~10`）。
- `delay` 必须有 `ms`（`10~600000`）。

### 3.5.5 导入校验清单（必须执行）

1. JSON 格式合法性校验（可解析）。
2. Schema 版本校验（`schemaVersion` 支持范围）。
3. 唯一性校验（`protocolId` 是否已存在）。
4. 命令键一致性校验（key 与 `cmd` 一致）。
5. 命令方向校验（与基线命令方向一致）。
6. 流程依赖校验（`requiresCommands` 与 `requiresParams` 可满足）。
7. 步骤完整性校验（`steps` 参数完整、类型合法、引用命令存在）。
8. 兼容性分级计算（`supported | partial | unsupported`）。

### 3.5.6 错误码建议（导入接口）

| 错误码 | 含义 | 建议处理 |
|---|---|---|
| `PROTO_IMPORT_JSON_INVALID` | JSON 语法错误 | 拒绝导入，提示行列位置 |
| `PROTO_IMPORT_SCHEMA_UNSUPPORTED` | schemaVersion 不支持 | 拒绝导入，提示支持版本范围 |
| `PROTO_IMPORT_PROTOCOL_ID_CONFLICT` | protocolId 冲突 | 提示“覆盖更新/取消” |
| `PROTO_IMPORT_CMD_KEY_MISMATCH` | 命令 key 与 cmd 不一致 | 拒绝导入并给出冲突命令 |
| `PROTO_IMPORT_CMD_DIRECTION_INVALID` | 命令方向非法或与基线冲突 | 标记命令无效并重算兼容性 |
| `PROTO_IMPORT_FLOW_DEP_MISSING` | 流程依赖命令/参数缺失 | 流程降级为 `partial/unsupported` |
| `PROTO_IMPORT_STEP_INVALID` | 步骤字段缺失或类型错误 | 拒绝导入并返回 step id |
| `PROTO_IMPORT_UNKNOWN` | 未知错误 | 记录日志并提示重试 |

- `ok=false` 时必须返回 `errorCode` 与可诊断的 `details`。

### 3.5.8 冲突与覆盖更新策略

当 `protocolId` 已存在时，导入行为必须显式指定 `onConflict`：

- `reject`：拒绝导入，返回 `PROTO_IMPORT_PROTOCOL_ID_CONFLICT`。
- `overwrite`：覆盖更新同 `protocolId` 的协议定义（保留同协议设备实例）。
- `fork`：自动生成新 `protocolId`（例如 `jx-v2.25-core-copy1`）后导入。

建议接口参数：

```json
{
  "payload": { "...": "协议JSON" },
  "onConflict": "reject",
  "dryRun": false
}
```

行为约束：

- `dryRun=true` 时仅返回校验结果与兼容性报告，不落库。
- `overwrite` 时需要记录变更摘要（命令新增/删除、流程新增/删除、字段变更）。
- `overwrite` 后必须触发：
  1. 全量流程兼容性重算；
  2. 当前打开控制面板刷新；
  3. 相关设备运行中流程的安全中止评估（必要时阻止覆盖）。

## 4. 协议与设备管理约束

- 拓扑图根节点改为“协议名”（来自内置协议或导入协议）。
- 同一套协议仅允许存在一份实例（按 `protocolId` 唯一约束）。
- 同名协议需判定为同一协议时，不允许重复新增，改为编辑或版本升级。
- 添加设备与协议后均需持久化存储，重启后可恢复。
- 支持协议与设备的修改：
  - 协议：名称、版本、命令映射、流程定义

## 8. 交互与状态联动

- 设备筛选条件变化后，拓扑图节点做增量刷新，不全量重建图实例。
- 点击桩节点：
  - 高亮该桩及关联枪/车路径。
  - 左侧抽屉打开并切换为该桩上下文。
  - 在抽屉中增加“该桩实时日志列表”区域（可与属性/控制同层或作为独立子区域）。
- 实时日志列表行为：
  - 日志窗口显示量来自插件配置 `maxVisibleLogs`，默认值 `5000`。
  - 每条日志默认展示：时间、命令、方向（接收/发送）、数据模式切换按钮（原数据/结构数据）。
  - 点击日志行后展开详情，展开内容至少包含：远端 IP、数据内容。
  - 数据内容展示受“原数据/结构数据”切换按钮影响：
    - 原数据：展示 Hex 原文（raw）。
    - 结构数据：展示解析后的结构化字段（structured）。
  - 当结构化数据不可用时，结构数据模式给出“无可用结构化数据”提示，不影响原数据显示。
- 切换或编辑协议后：
  - 重新计算全部流程兼容性。
  - 控制面板中不可用流程置灰并显示原因（缺失命令/参数）。
- 流程执行中的步骤结果实时写入“该桩实时日志列表”，并同步更新：
  - 桩状态
  - 枪状态
  - 车辆绑定关系

---

## 9. 异常与容错

- TCP 连接失败：显示连接失败状态，支持手动重连。
- 命令超时：按流程配置重试，超出次数后流程失败。
- 非法 Hex 命令：前置校验并阻止发送。
- 远端返回未知报文：记录原始帧，标记“未识别响应”。
- 协议导入冲突：同 `protocolId` 已存在时阻止重复创建，提供“覆盖更新/取消”。
- 协议导入缺失：流程依赖命令或参数缺失时，流程自动降级为受限/不可用。

## 12. 实时日志交互线框规范（选中桩）

## 12.1 布局分区

选中桩后，左侧抽屉建议分为三层：

1. 顶部：桩基础信息摘要（桩编号、状态、在线标识）
2. 中部：`属性信息 / 控制面板` Tab 内容
3. 底部：实时日志区（固定标题 + 工具栏 + 日志列表）

日志区在抽屉内为独立滚动容器，避免影响属性与控制区域阅读。

## 12.2 日志工具栏

建议包含：

- 关键字检索（命令、IP、原始数据片段）
- 方向筛选（全部 / 发送 / 接收）
- 数据模式切换（原数据 / 结构数据）
- 清空当前桩日志按钮（可选，需二次确认）
- 自动追尾开关（默认开启）

## 12.3 行级展示（折叠态）

每行固定展示：

- 时间（`HH:mm:ss.SSS`）
- 命令
- 方向（发送/接收，颜色区分）
- 数据模式按钮（原数据 / 结构数据）
- 展开箭头

交互要求：

- 点击整行或箭头展开该条日志详情
- 数据模式按钮切换后，仅影响当前条展示或按“全局模式”统一（建议全局模式，提升一致性）

## 12.4 展开态详情

展开后展示：

- 远端 IP（含端口）
- 数据内容：
  - 原数据模式：Hex 原文分组显示（建议按字节分组）
  - 结构数据模式：JSON/键值结构化展示

补充规则：

- 结构化数据不存在时，显示“当前日志无结构化数据”
- 长内容支持复制按钮（复制原文/复制结构）

## 12.5 展开策略

默认策略建议：

- 仅允许单条展开（新展开自动收起上一条），降低长列表视线跳跃
- 可配置为“多条展开”（调试场景）

## 12.6 自动追尾与滚动定位

- 自动追尾开启时：
  - 新日志到达自动滚动到底部
- 自动追尾关闭时：
  - 新日志只更新计数，不打断当前阅读位置
  - 提供“跳到最新”快捷按钮

定位策略：

- 切换桩后滚动重置到最新
- 切换筛选条件后保持当前锚点；若锚点消失则回到列表顶部

## 12.7 性能与显示上限

- 采用“环形缓冲”或“定长队列”保留最近 `maxVisibleLogs` 条（默认 `5000`）。
- 对单条超长日志可启用内容折叠与按需渲染（避免一次性渲染大文本）。
- 高频日志场景建议使用虚拟列表，确保抽屉滚动流畅。

## 12.8 状态与颜色建议

- 发送：主色系（蓝/青）
- 接收：中性色或绿色系
- 异常日志：红色强调（解析失败、超时、协议错误）
- 已展开行：背景轻微高亮

## 13.2 关键组件职责

  - 提交筛选条件变更事件，不直接操作拓扑

- `JXPileDrawer`
  - 订阅“当前选中桩”状态
  - 管理 Tab 切换与日志区域显示
- `JXControlPanelTab`
  - 读取流程兼容性结果
  - 对不可执行流程置灰并展示缺失项
- `JXRealtimeLogPanel`
  - 管理日志筛选、模式切换、追尾策略
  - 维护展开态键集合（单开或多开）

## 13.3 Pinia 状态分层建议

建议拆分为 3 个 Store：

1. `useProtocolStore`
   - 协议清单、当前协议、导入/导出、兼容性结果
2. `useTopologyStore`
   - 节点数据（协议/桩/枪/车）、当前选中桩、筛选结果
3. `useRuntimeLogStore`
   - 按 `pileId` 分组日志队列
   - 日志显示配置（`maxVisibleLogs`、追尾开关、当前模式）

## 13.4 推荐事件流

### A. 点击拓扑桩节点

1. `JXTopologyCanvas` 捕获点击事件，派发 `selectPile(pileId)`
2. `useTopologyStore` 更新 `activePileId`
3. `JXPileDrawer` 打开并渲染对应桩上下文
4. `useRuntimeLogStore` 切换当前日志视图到该 `pileId`

### B. 执行流程

1. 控制面板点击“执行流程”
2. `ProtocolExecutor` 按步骤执行 `send/expect/branch...`
3. 每步输出写入 `useRuntimeLogStore.appendLog(pileId, entry)`
4. 同步更新 `useTopologyStore` 中桩/枪/车状态

### C. 导入协议

1. 读取协议 JSON
2. 进行 schema 与命令完整性校验
3. 写入 `useProtocolStore`
4. 触发兼容性重算并刷新控制面板可执行状态

## 13.5 IPC 与后端桥接建议（Electron）

如果 TCP 在主进程执行，建议桥接通道：

- `jx:protocol:import`
- `jx:protocol:export`
- `jx:flow:execute`
- `jx:flow:stop`
- `jx:tcp:connect`
- `jx:tcp:disconnect`
- `jx:log:stream`（主进程推送日志到渲染层）

渲染层仅消费“结构化事件”，不直接管理底层 socket。

## 15. 协议 V2.25 流程命令映射（实现基线）

以下映射基于 `玖行桩协议2.25.md` 的命令定义与字段表，用于首版流程配置默认模板。

## 15.1 链接认证登录流程

建议命令序列：

1. `0x01` 桩请求连接（上行）
2. `0x02` 请求连接结果（下行）
3. `0x03` 登录信息（上行）
4. `0x04` 请求连接结果（下行）
5. 周期维持：
   - `0x0B` 平台心跳（下行）
   - `0x0C` 桩心跳（上行）

执行判定：

- `0x02/0x04` 返回成功码则进入已连接状态
- 拒绝码进入失败分支并记录原因

## 15.2 远端控制启动流程

建议命令序列：

1. `0x1F` 平台下发充电命令（下行）
2. `0x20` 桩回复充电命令（上行）
3. `0x21` 桩启动充电结果（上行）
4. `0x22` 平台回复桩启动充电结果（下行）
5. 充电过程上报：
   - `0x25` 充电桩工作信息（上行）
6. 结束：
   - `0x26` 平台下发停止充电命令（下行）
   - `0x27` 桩回复停止充电命令（上行）

## 15.3 本地 VIN 启动流程

建议命令序列（按 V2.25 第 3 章已收敛命令）：

1. `0x59` 远方获取VIN码（下行，可选）
2. `0x5B` 回复远方获取VIN码（上行，可选）
3. `0x46` 插枪上报VIN信息（上行）
4. `0x47` 回复插枪上报VIN信息（下行）
5. `0x40` 桩请求VIN鉴权（上行）
6. `0x41` 平台回复VIN鉴权（下行）
7. 鉴权后进入 `0x21 -> 0x22` 结果确认链路

## 15.4 远端控制启动 VIN 鉴权流程

建议命令序列：

1. `0x40` 桩请求VIN鉴权（上行）
2. `0x41` 平台回复VIN鉴权（下行）
3. 鉴权后进入 `0x21` 桩启动充电结果（上行）
4. 平台返回 `0x22` 回复桩启动充电结果（下行）

## 15.5 流程配置中的依赖声明建议

每条流程模板显式声明命令依赖，用于导入协议后的可用性判定：

```json
{
  "flowId": "remote-start",
  "requiresCommands": ["0x1F", "0x20", "0x21", "0x22"],
  "requiresParams": ["pileId", "gunId", "vin?"]
}
```

若导入协议缺少依赖命令：

- 核心命令缺失 -> `unsupported`
- 非核心命令缺失 -> `partial`

## 15.6 核心命令报文字段（V2.25 对齐）

以下字段摘自 `平台与玖行电桩通信协议V2.25.docx` 对应报文表，用于流程参数面板与报文解析器落地。

### 15.6.1 链接与登录（`0x01~0x07`）

| 命令 | 关键字段 | 说明 |
|---|---|---|
| `0x01/0x02` | 时间标识、请求结果、拒绝连接原因、二维码固定段、二维码枪号段数量/明细 | 连接受理与扫码二维码下发 |
| `0x03/0x04` | 时间标识、桩型号、软硬件版本、模块信息、心跳周期、遥信/遥测周期 | 登录参数与连接确认 |
| `0x05` | 时间标识 | 请求对时 |
| `0x06` | 时间标识、对时时间 | 平台下发对时 |
| `0x07` | 时间标识、对时结果、失败原因 | 对时应答 |

### 15.6.2 远端启动/停止（`0x1F~0x27`）

| 命令 | 关键字段 | 说明 |
|---|---|---|
| `0x1F` | 枪号、订单号、用户ID、用户类型、组织机构代码、控制方式、控制参数、充电模式、启动方式、定时启动时间、用户操作码、计费模型选择、执行结果、失败原因 | 平台下发启动充电主命令 |
| `0x20/0x21/0x22` | 与 `0x1F` 关联的订单号、执行结果、失败原因 | 启动链路应答与结果确认 |
| `0x26` | 时间标识、枪号、充电订单号 | 平台下发停止充电 |
| `0x27` | 时间标识、枪号、充电订单号、停止结果 | 桩回复停止结果（`0=成功`、`1=订单号不一致`） |

### 15.6.3 VIN 鉴权（`0x40~0x47`）

| 命令 | 关键字段 | 说明 |
|---|---|---|
| `0x40/0x41` | 时标、VIN、账户余额、允许充电标志、不可充电原因、计费模型选择、计费模型版本、停车费费率、时段数N、分段费率、充电订单号 | VIN 鉴权请求/应答核心参数 |
| `0x46/0x47` | VIN、枪号、订单号（及应答结果） | 插枪VIN上报与平台确认 |

实现建议：

- 将上述“关键字段”同步到 `commandCatalog` 中，作为 `requiredParams` 的默认来源。
- `0x1F`、`0x40` 解析器实现时优先采用“最小可执行字段集”，其余字段可逐步扩展到全字段。
- 对于导入协议缺失字段，按 `missingParams` 输出到流程兼容性报告。

## 15.8 协议导入后的自动校验规则

### 15.8.1 命令存在性校验

- 连接登录流程：必须包含 `0x01/0x02/0x03/0x04`。
- 远端启动流程：必须包含 `0x1F/0x20/0x21/0x22`，建议包含 `0x25`。
- 停止流程：必须包含 `0x26/0x27`。
- VIN 鉴权流程：必须包含 `0x40/0x41`；插枪链路按场景可选 `0x46/0x47`。

### 15.8.2 字段能力校验

- 若 `0x1F` 缺少 `orderNo` 或 `gunNo`，则禁止创建“远端启动”流程实例。
- 若 `0x41` 缺少 `allowChargeFlag`，则 VIN 鉴权结果不可判定，流程强制失败。
- 若 `0x25` 缺少 `chargeEnergy` 与 `chargeAmount`，则允许流程运行，但“订单统计与计费看板”标记为受限能力。
- 若 `0x23/0x33/0x61` 缺少 `orderNo`，则关闭“订单补录/召唤”功能入口。

### 15.8.3 方向一致性校验

校验导入协议中命令方向是否与基线一致（上行/下行）：

- 不一致时标记 `invalidDirection`，该命令不参与流程执行。
- 若该命令是流程核心命令，则流程直接降级为 `unsupported`。

## 15.9 解析与日志落地建议（对齐第 12 章日志面板）

- 每条报文先保留 `rawHex`，再写入 `structured`（解析成功时）。
- `structured` 最小公共字段：
  - `cmd`
  - `direction`
  - `timeTag`
  - `gunNo?`
  - `orderNo?`
  - `vin?`
  - `resultCode?`
  - `reasonCode?`
- 对 `0x25/0x23/0x33/0x61` 的分段字段，统一存到 `structured.segments[]`。
- 解析失败时仍入库日志，`structured = null`，并写 `parseError`，确保调试可回放。
